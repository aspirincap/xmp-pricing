# XMP 商务报价业务规则

本文定义需求解析、套餐推荐、加购、减去项和报价输出口径。Skill 初始化时读取两个官方 CNY/USD 页面并保存核验快照；后续报价复用该快照，并将初始化获取时间写入输出。需要更新价格时重新运行初始化脚本。模型只负责理解输入，不得凭记忆补价格或自行换汇。

## 1. 统一术语

- 对外统一使用“套餐官方活动价”“原活动价总价值”“调整后活动价”，不要使用“刊例价”。
- `原活动价总价值 = 套餐官方活动价 + 必要加购`。
- `调整后活动价 = max(0, 原活动价总价值 - 减去项合计)`。
- `6/7/8/9 折报价 = 调整后活动价分别 × 60%/70%/80%/90%`。
- 两类 Ad 额度必须分开称呼和核算：
  - “每月 Ad 创建额度”，单位为“万/月”；
  - “不过期 Ad 创建总额度”，单位为“万”。
- 不要用“Ad 创建总额度”代替“不过期 Ad 创建总额度”，也不要让两类额度互相抵扣。

## 2. 自然语言解析

先将用户原文转换成结构化需求，再做任何价格计算。每个字段保留原文证据和是否明确给出，避免把“没有提到”误当成“明确不要”。

### 2.1 三态字段

API、流量池、一键试新及其他开关型能力使用三态值：

- `required`：明确需要、要、包含或数量大于 0；
- `not_required`：明确说不要、不需要、取消或去掉；
- `unspecified`：未提及或无法判断。

`unspecified` 不产生加购，也不自动产生减去项。只有 `not_required` 才能触发套餐内已含权益的自动扣减。

通用“API”默认指“标准 Report API”；出现“归因、Attribution、归因数据”等词时才指“归因数据 API”。“两个 API 都不要”“所有 API 不要”等明确复数表达同时作用于两类 API；仍有歧义时列入待确认项。

### 2.2 数量、金额与折扣

- `w/W/万` 结合上下文解析。出现在 Ad、用户、账户、额度等名词附近时优先视为数量；出现在报价、回款、金额、人民币、美元等词附近时视为金额。
- “50w 不过期 Ad”表示“不过期 Ad 创建总额度 50 万”，不能解析成报价 500,000，也不要在展示中写成“50 个 1 万”。计价时可按价格表的每万单价计算，但展示真实总额度、计价单位和小计。
- “全年 144 万（每月 12 万）”以每月峰值 12 万作为“每月 Ad 创建额度”，144 万只用于一致性校验。若只有全年总量而没有月峰值，不得默认除以 12；先要求确认月峰值或标记为待确认。
- “12500 × 0.9”“12500 的九折”“12500*0.9折”等商务口语均按乘数 0.9 计算为 11,250；同时保留原表达，避免把“0.9折”按字面算成 9%。
- 数字中的逗号、空格和中英文单位先标准化，再校验是否为非负数。

### 2.3 媒体分类

- 大媒体包括 Meta/Facebook/FB、Google、TikTok/TT、Snapchat、Kwai 和 Apple Ads/ASA 等价格表认可的大媒体。别名归一化并去重，例如“TT TikTok”只算 1 个。
- Mintegral、Unity、AppLovin、Liftoff 等属于视频渠道。
- 只有大媒体消耗大媒体额度并可能产生渠道加购费用。视频渠道不消耗大媒体额度，也不产生额外渠道费用。
- 若套餐表规定视频渠道容量，仍需校验容量；超过容量时将该方案标记为不满足或待人工确认，不得虚构视频渠道单价。
- 无法确定分类的媒体先列入待确认项，不要擅自归为大媒体以增加报价。

### 2.4 冲突与上下文

- 多轮或聊天记录中，以“最终、确认、改成、取消、不要、按这个”等明确的最后决策为准。
- 同一字段出现冲突且没有最终决策信号时，不静默选择其中一个；列出冲突值并请求最少量确认。
- 用户指定币种时只用对应官方价格表，不做汇率换算。未指定币种时，默认分别输出人民币与 USD 两套结果，并明确它们是独立价格体系。
- 用户明确指定套餐时，按该套餐模拟，同时保留自动推荐结果用于对比；不要偷偷替换用户指定的套餐。
- 区分总需求表达与报价组合表达。“客户使用 1 个大媒体”表示总需求 1 个；“基础版 + API + 1 个大媒体”表示锁定基础版，并在基础版自带 1 个大媒体之外再加购 1 个，因此结构化总需求为 2 个。加号语义仍不清时再追问。

## 3. 套餐能力与必要加购

对基础版、高级版、专业版和 VIP 版逐一试算：

1. 先检查硬性能力是否满足。套餐不具备且不能加购的能力会使方案失效。
2. 对可计量项目先抵扣套餐已含数量：`净增购需求 = max(客户需求 - 套餐已含, 0)`。
3. 按项目计价单位向上取整得到加购计价数量，再乘对应币种活动单价。
4. 套餐已含的能力不得重复收费。
5. 将套餐官方活动价与全部必要加购相加，得到该套餐的“原活动价总价值”。

常见能力规则：

- 标准 Report API、归因数据 API：明确需要且套餐未含时才加购；套餐已含时仅展示“已覆盖”。
- 流量池：明确需要且套餐未含时按所选套餐对应价格加购；若该加购附赠一键试新次数，将赠送次数计入试新可用额度，避免重复购买。
- Mintegral 一键试新：先抵扣套餐自带次数和流量池附赠次数，只对超出部分计价。
- 自动创建广告、素材能力、AI 视频、投放诊断、高频模式和数据接入套餐按价格表中的能力门槛、系数或固定价格处理；缺少明确价格时转人工确认。
- 每月 Ad 创建额度与不过期 Ad 创建总额度独立加购；任一额度都不能替代另一额度。

## 4. 套餐推荐

自动推荐遵循以下顺序：

1. 排除不满足硬性能力或容量要求的方案。
2. 按“原活动价总价值”从低到高排序，选择最低者。
3. 同价时依次选择必要加购项目更少、套餐档位更低的方案。
4. 减去项不参与套餐排名，因为它是选定套餐后的商务调整，不能用未使用权益反向操纵套餐推荐。
5. 若所有标准套餐都不满足，输出“需要定制/人工确认”，并列明每档缺口，不给出伪精确推荐。

推荐说明必须包含推荐套餐、满足需求的理由、次优方案及差额；四档方案对比均使用各自未扣减前的“原活动价总价值”。

## 5. 减去项

减去项用于内部商务灵活报价，不代表官网承诺退费。最终输出应把“原活动价总价值”和“减去项”分别列明，确保调整可追溯。

### 5.1 可扣目录

- 可扣目录与当前币种的加购项目录一致。
- 唯一强制排除项是“不过期 Ad 创建总额度”；无论自动还是用户手动指定，都不得把它作为减去项。
- 视频渠道没有付费加购价，因此也不会凭空成为减去项。
- 某权益在所选套餐/币种下没有确定的参考单价时，不计算扣款，转为待人工确认。

### 5.2 自动生成条件

只有用户给出明确需求时才自动扣减：

- 明确给出数量且低于套餐已含数量：可扣未使用部分。例如套餐含 4 个大媒体、客户明确只要 TT 和 FB，则生成“未使用大媒体额度 2 个”。
- 明确说某能力“不要”：若所选套餐确实包含该能力，按可扣目录生成对应减去项。例如“标准 API 不要”可扣套餐内含的标准 Report API；“试新不要”可扣套餐内含的试新次数。
- 未提及的权益保持 `unspecified`，不自动扣减。
- 客户需求等于或高于套餐已含数量时，不生成该项目的未使用额度扣减。
- 用户明确说“不做任何减去项”时，设置 `deduction_mode: none`，跳过自动与手动减去项；其他情况默认 `auto`。

自动扣减只针对所选套餐实际包含且未使用的权益。定量项目按完整计价单位向下取整可扣数量，避免对不足一个计价单位的剩余额度过度扣减；定性项目按 1 项处理。

### 5.3 手动商务调整

用户可明确指定“减去某项及数量”。仍需校验项目在可扣目录中、数量非负、币种单价存在，并单独标记为“手动商务调整”。若数量超出套餐已含或已计价数量，保留用户意图但发出人工复核警告，不得掩盖异常。

同一权益不得因“未使用额度”和“明确不要”重复扣减，也不得同时从加购和套餐权益中重复扣减。减去项合计若超过原活动价总价值，将调整后活动价限制为 0，并输出高优先级警告。

## 6. 单位与取整

- 大媒体：按 1 个计价；别名去重后计数。
- 每月 Ad 创建额度：需求和套餐额度使用“万/月”；加购按价格表规定的每万/月单位向上取整。
- 不过期 Ad 创建总额度：使用“万”；加购按价格表规定的每万单位向上取整，但展示为完整总额度。
- 广告账户：按每 100 个为一个计价单位；净增购不足 100 个也按 1 个计价单位收费。
- 用户、AI 助手规则、定时报表、YouTube 频道、子渠道应用和试新次数：按价格表单位向上取整。
- 素材库容量：按价格表规定的 T 单位向上取整。
- 自动减去未使用额度时使用完整计价单位向下取整；用户明确手动调整时按用户数量计算并标记复核风险。
- 所有中间数量保留计算所需精度；最终金额按当前价格表约定取整到币种整数。6、7、8、9 折及最终折扣均基于同一个“调整后活动价”，避免混用未扣减总额。

## 7. 报价与折扣

按下列公式固定计算：

```text
原活动价总价值 = 套餐官方活动价 + 必要加购合计
调整后活动价 = max(0, 原活动价总价值 - 减去项合计)
6折报价 = round(调整后活动价 × 0.60)
7折报价 = round(调整后活动价 × 0.70)
8折报价 = round(调整后活动价 × 0.80)
9折报价 = round(调整后活动价 × 0.90)
最终核算折扣 = 实际报价金额 ÷ 调整后活动价 × 10
```

- 用户未提供实际报价时，以 9 折报价作为“建议实际报价金额”，显示建议折扣 9.00 折；不要声称这是用户已经确认的实际报价，并同时展示 6/7/8/9 折报价。
- 用户提供具体报价金额时，只展示该报价相对调整后活动价的最终折扣，不展开 6/7/8/9 折金额。
- 用户提供实际报价或计算表达式时，展示实际报价以及相对调整后活动价的最终核算折扣。
- 折扣只保留一个口径：`final_discount` 的分母固定为调整后活动价。不要计算或展示实际报价相对原活动价总价值的折扣。
- 不再输出“6 折最低价”或基于该口径的审批警告；如需审批，由商务另行指定审批规则。
- 调整后活动价为 0 时不计算最终折扣，输出“无法计算”及扣减异常警告，避免除以零。

## 8. 待确认逻辑

出现以下情况时列入 `warnings` / “待确认项”；会显著改变套餐或金额时，先向用户提出一个最小化问题：

- 只有全年 Ad 总量，没有每月峰值；
- `w/W/万` 无法判断是金额还是额度；
- 未知媒体或无法判断大媒体/视频渠道；
- 同一需求存在多个相互冲突的版本；
- “API”指代不明且不同 API 会改变扣减或加购；
- 所需能力没有价格、套餐容量或可售规则；
- 手动减去项超过所选套餐已含或已计价数量；
- 减去项合计超过原活动价总价值；
- 所有标准套餐均不满足；
- 输入的全年量与月度量明显不一致，例如全年量不等于明确月度量乘 12，且用户未说明峰谷变化。

不要因某个可选字段缺失而阻塞全部结果。能确定的部分先试算，将假设和未确定项明确列出；但不得用猜测生成正式报价。

## 9. 固定输出字段

结构化结果固定包含以下顶层字段；没有值的可选字段使用 `null` 或空数组，不要省略关键价格字段：

```text
recommended_plan
recommendation_mode
currency
demand_summary
actual_quote
suggested_quote
final_discount
original_activity_total
deduction_total
adjusted_activity_total
recommended_price_90
minimum_price_60（兼容旧字段，不在人类可读结果中展示）
discount_prices（6折、7折、8折、9折）
components
deductions
coverage
quota_summary
calculation_trace
plan_comparison
recommendation_reason
warnings
pricing_source
pricing_version
```

明细字段要求：

- `components[]`：`item_id`、`label`、`requested`、`included`、`extra`、`display_unit`、`billing_quantity`、`billing_unit`、`unit_price`、`subtotal`、`detail`。
- `deductions[]`：上述计价字段外，增加 `reason`、`mode`（`auto` 或 `manual`）和 `source_requirement`。
- `coverage[]`：逐项列出客户需求、套餐已含、净增购和最终覆盖数量。
- `quota_summary.monthly_ad_creation`：套餐已含、客户需求、额外加购、最终“每月 Ad 创建额度”。
- `quota_summary.non_expiring_ad_creation_total`：客户需求、额外加购、最终“不过期 Ad 创建总额度”。两者禁止合并。
- `plan_comparison[]`：套餐名、是否满足、失效原因、套餐官方活动价、必要加购合计、原活动价总价值、与推荐方案差额。
- `pricing_source`：列出对应币种官方链接；`pricing_version` 标明价格表版本或抓取日期。

## 10. 固定的人类可读报告

按以下顺序输出，金额都带币种符号：

1. **需求识别**：币种、大媒体及视频渠道、两类 Ad 额度、用户、广告账户、API/流量池/试新等三态需求。
2. **核心结论**：推荐套餐、实际/建议报价、当前报价相对调整后活动价的折扣，并列出原活动价总价值、减去项合计、调整后活动价和 6/7/8/9 折报价。
3. **计算公式与明细**：套餐官方活动价、每条必要加购、每条减去项、单价、真实数量、计价数量和小计。
4. **计算推演**：完整展示加总、扣减、6/7/8/9 折；有实际报价时，只展示相对调整后活动价的折扣公式。
5. **Ad 额度汇总**：分别展示“每月 Ad 创建额度”和“不过期 Ad 创建总额度”。
6. **套餐额度抵扣**：逐项展示“客户需求 - 套餐已含 = 净增购/未使用额度”。
7. **套餐推荐说明与四档对比**：说明推荐理由、次优差额、能力缺口和是否为指定套餐模拟。
8. **待确认项与价格来源**：列出风险、活动价口径、CNY/USD、官方链接和价格版本。

报价构成示意应采用以下表达，不省略套餐已含和计价单位：

```text
专业版（套餐官方活动价）                         $12,500
+ 每月 Ad 创建额度：需求 12 万/月 - 已含 7 万/月
  = 增购 5 万/月 × $1,400/万/月                  $7,000
- 未使用大媒体额度：已含 3 个 - 明确需求 2 个
  = 减去 1 个 × $2,800/个                       -$2,800
```

## 11. 典型输入的解析校验

输入：

```text
媒体数量：TT FB
全年需要 AD 总数：144 万（每月 12 万）
用户数：120 个
广告账号：7000 个，API 和试新不要
```

应识别为：

- 大媒体为 TikTok、Facebook，共 2 个；没有视频渠道需求。
- 每月 Ad 创建额度为 12 万/月；全年 144 万仅用于核对，不转成不过期额度。
- 用户 120 人，广告账户 7,000 个。
- 标准 Report API 为 `not_required`；一键试新为 `not_required`；归因数据 API 为 `unspecified`。
- 对每档套餐先按上述需求计算原活动价总价值并推荐；选定套餐后，才对明确未使用的大媒体、标准 Report API 和一键试新权益生成减去项。
- 未提到的套餐权益不得自动扣减；不过期 Ad 创建总额度始终不得进入减去项。

## 12. 价格依据

- USD：https://help-xmp.mobvista.com/docs/xmp_price_usd
- CNY：https://help-xmp.mobvista.com/docs/xmp_price_cny

计算时优先使用 Skill 内已校验的对应币种价格参考文件。价格表缺项、版本过期或官方页面发生冲突时，停止对冲突项目给出正式金额并提示更新价格参考。

每次正式报价还必须记录：

- `pricing_check_status`：初始化双页面检查状态，正式报价必须为 `verified`；
- `pricing_checked_at`：初始化获取官方报价单的 Asia/Shanghai 时间戳；
- `pricing_check_sources`：初始化读取的 USD 与 CNY 官方 URL、页面标题、页面修改日期和内容哈希。
